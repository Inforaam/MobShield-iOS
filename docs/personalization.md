# Build personalization

This page covers what the `mobshield-personalize.sh` build phase does, when it has any effect, and
why it keeps no secrets.

## What it does

The script generates `mobshield_buildinfo.h` in the target's `DERIVED_FILE_DIR`. The header sets:

- `MOBSHIELD_BUILD_ID`: `ios-` followed by 16 hex characters derived from a random seed (or from
  `MOBSHIELD_RANDOM_SEED`, if you set it). It is a **public identifier**, safe to log.
- `MOBSHIELD_EXPECTED_SIGNER_SHA256`, `MOBSHIELD_EXPECTED_BUNDLE_ID`, `MOBSHIELD_EXPECTED_TEAM_ID`
  and `MOBSHIELD_AGGRESSIVE_ANTI_DEBUG`, from your build settings. The native code does not read
  these; the runtime integrity checks use the values you pass to `MobShieldConfig`.

`mobshield-verify.sh` runs after linking. It checks the signing certificate against
`MOBSHIELD_EXPECTED_SIGNER_SHA256`, and looks for `MOBSHIELD_BUILD_ID=<this build's ID>` in the app
bundle, which is only there if MobShield's native code was compiled with this build's header.

## It usually has no effect on the binary

MobShield's native core includes the `mobshield_buildinfo.h` bundled with the package. A header
generated into your target's derived files only replaces it if MobShield's native sources are
compiled with that directory ahead of the bundled header.

- **Swift Package Manager:** package targets are built with their own settings, so the bundled header
  is always used. The binary, and `MobShield.getBuildId()`, are the same in every app that uses the
  same MobShield release.
- **CocoaPods:** the pod runs the script as its own build phase. Whether the generated header wins
  depends on header search order; `mobshield-verify.sh` tells you. If it warns that the build ID was
  not found, the binary is the release's.

The verify script reports this as a warning rather than a failure.

## One bypass fits every app on the same release

Because the shipped binaries are identical, a hook script or patch that defeats a MobShield release
works against every app using that release. Changing a few constants per build would not change that
much: bypass tools target function names, behaviour and code patterns, not constants.

Plan for it:

- Make decisions that matter on your server, from App Attest-backed reports
  ([report-attestation.md](report-attestation.md)), not from the client's word.
- Treat termination as a deterrent ([termination.md](termination.md)).

## There are no secrets in the app

Anything that ships in an app can be read by whoever has the app. MobShield therefore generates
nothing that is meant to stay secret, and the header and the binary contain no keys.

Earlier versions did:

- The script derived 16 bytes of "build entropy" and used them as an AES-GCM key and as an HMAC key.
- It wrote the entropy into the header. The native core embedded it behind a searchable
  `MOBSHIELD_ENTROPY=` marker, and the build ID carried its first 8 hex characters.
- The encrypted data was 64 bytes of `0xFF`, and no native code read it. The native-library HMAC and
  the symbol-rename macros were not used either. Had the header reached the native core, the rename
  of `mobshield_native_self_check` would have broken linking.

The "encryption" protected nothing. All of it has been removed. With Swift Package Manager the
generated header never reached the native core, so the entropy did not end up in those binaries.

Hook prologue and swizzle baselines are not generated by the script; you supply them in
`MobShieldConfig` (see [detection/ios-hooks.md](detection/ios-hooks.md)).

## Changes in this version

- The build ID is `ios-<16 hex>`, derived separately from the seed, and is documented as public.
- The generated and bundled headers no longer contain `MOBSHIELD_BUILD_ENTROPY`, the AES-GCM nonce
  and ciphertext, the key-derivation salt, `MOBSHIELD_NATIVELIB_HMAC`, or symbol-rename macros.
- The native core embeds `MOBSHIELD_BUILD_ID=<id>` instead of `MOBSHIELD_ENTROPY=<entropy>`.
- `mobshield-verify.sh` checks for the build ID and warns, in every configuration, when the native
  code was not built with this build's header. It previously failed Release builds in that case.
